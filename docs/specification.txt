Техническое задание: Math Hero — тренажёр математического автоматизма

MVPiPhone / iPadРусский / Español

Я предлагаю немного изменить первоначальную концепцию. Мы делаем не детскую игру с математическими заданиями, а серьёзный адаптивный тренажёр с игровой оболочкой.

Его главная задача — довести таблицу умножения до устойчивого автоматизма, чтобы ребёнок перестал тратить рабочую память на вычисление простых произведений и мог сосредоточиться на более сложных операциях.

При этом архитектура должна позволить в будущем добавить:

* деление;
* умножение двузначных и трёхзначных чисел;
* деление многозначных чисел;
* вычисления в столбик;
* смешанные арифметические упражнения.

Но сейчас мы полностью закрываем только одну задачу: автоматическое воспроизведение результатов таблицы умножения от 1 до 12.

Ни голосового ввода, ни текстовых задач, ни сложной игровой механики в первой версии не будет.

1. Концепция продукта

1.1. Для кого приложение

Основной пользователь:

* ребёнок 8–9 лет;
* родной язык — русский;
* обучение в испаноязычной образовательной среде;
* знает таблицу умножения, но недостаточно быстро вспоминает ответы;
* занимается на iPad или iPhone.

Второй пользователь — родитель, который:

* запускает приложение;
* видит прогресс;
* может оценить слабые места;
* понимает, действительно ли формируется автоматизм.

1.2. Основная образовательная цель

Не просто научить ребёнка правильно отвечать на примеры.

Нужно добиться следующего результата:

* Ребёнок видит пример.
* Правильный ответ извлекается из памяти без последовательного сложения.
* Ответ воспроизводится быстро.
* Навык сохраняется через несколько дней.
* Навык работает в перемешанном порядке, а не только внутри одной таблицы.

Это и будет критерием успешности продукта.

1.3. Принципы разработки

Принцип	Решение
Простота	Минимум экранов и действий
Мобильность	Сначала проектируем под iPhone и iPad
Обучение	Retrieval practice + spaced practice
Адаптация	Индивидуальная сложность для каждого примера
Мотивация	Персонаж, опыт, достижения
Двуязычность	Русский и испанский интерфейс
Автономность	Без сервера и регистрации
Расширяемость	Математические операции как отдельные модули

2. Технологический стек

Я рекомендую сразу отказаться от идеи одного большого HTML-файла.

Для первого прототипа это допустимо, но для проекта, который будет развиваться, правильнее использовать нормальную структуру React-приложения.

Архитектура технологий

React

Компоненты интерфейса

CSS

Адаптивный дизайн

Vite

Сборка приложения

IndexedDB

История и прогресс

GitHub Pages

Статический хостинг

Почему IndexedDB вместо localStorage:

* больше возможностей для структурированного хранения;
* история большого количества попыток;
* отдельные записи для каждого математического факта;
* возможность добавлять новые типы упражнений;
* более удобная миграция структуры данных.

Никакого backend, авторизации и облачной базы в MVP не требуется.

Важное ограничение: данные останутся на конкретном устройстве и в конкретном браузере. При очистке данных Safari они могут потеряться. Поэтому в MVP обязательно предусмотрим экспорт и импорт резервной копии.

3.1. Главный экран

На главном экране:

* персонаж — например, маленький космический лис;
* приветствие;
* количество заработанных звёзд;
* процент освоенных примеров;
* кнопка «Начать тренировку»;
* кнопка «Мои трудные примеры»;
* кнопка «Мои результаты»;
* переключение языка RU / ES.

Не нужно делать большое меню с десятками режимов.

3.2. Экран тренировки

Основной экран должен содержать:

* Один пример крупным шрифтом.
* Большое поле ввода ответа.
* Цифровую клавиатуру.
* Кнопку подтверждения.
* Индикатор прогресса занятия.
* Персонажа с короткими реакциями.
* Небольшую информацию о результате.

3.3. Экран результатов

Ребёнок видит:

* сколько примеров решил;
* сколько было правильных ответов;
* сколько примеров стало лучше;
* сколько звёзд получил;
* какое достижение открыл.

Родитель дополнительно видит:

* среднее время ответа;
* точность;
* самые сложные примеры;
* изменение скорости по дням;
* сколько примеров устойчиво освоено.

Не нужно показывать ребёнку длинные таблицы статистики. Подробная аналитика — отдельная часть интерфейса для взрослого.

3.4. Карта таблицы умножения

В приложении должна быть сетка 12 × 12.

Каждая ячейка имеет цветовой статус:

Цвет	Значение
Серый	Ещё не проверялся
Красный	Есть ошибки или затруднения
Жёлтый	Формируется навык
Голубой	Хорошая скорость и точность
Зелёный	Устойчивый автоматизм

При нажатии на ячейку можно посмотреть историю конкретного примера и потренировать его отдельно.

Особенность: математически 7 × 8 и 8 × 7 дают один и тот же факт благодаря переместительному свойству. Но оба направления должны встречаться в заданиях. Внутренний учёт мастерства будет учитывать это обстоятельство, чтобы не создавать искусственно двойную нагрузку.

4. Методика формирования автоматизма

Это центральная часть проекта. Её нельзя оставлять внутри React-компонентов или реализовывать несколькими случайными условиями.

Нужен самостоятельный модуль training-engine.

4.1. Состав математического материала

Таблица включает:

* множители от 1 до 12;
* множимое от 1 до 12;
* 144 направленных задания;
* 78 уникальных пар с учётом переместительного свойства.

Каждый направленный пример может появляться в обеих ориентациях.

Например:

* 7 × 8 = 56;
* 8 × 7 = 56.

В базе сохраняются данные об обоих направлениях, но общий уровень мастерства учитывает и совокупную историю пары.

4.2. Этап 1 — начальная диагностика

При первом запуске предлагается пройти диагностику.

Она должна:

* включать все 144 направления;
* перемешивать задания;
* не показывать таймер обратного отсчёта;
* фиксировать точность;
* измерять время ответа;
* сохранять ошибки.

Диагностика должна быть разделена на несколько коротких частей, например по 24 задания.

Ребёнок может остановиться и продолжить позже.

Задача диагностики — не выставить оценку, а получить исходную модель знаний.

Важно: на первом прохождении не следует сразу считать медленный правильный ответ освоенным фактом.

4.3. Этап 2 — адаптивная тренировка

Это основной режим, который ребёнок будет использовать ежедневно.

Принцип подбора:

Состояние примера	Частота
Не проверялся	Высокая
Есть ошибки	Очень высокая
Правильный, но медленный	Высокая
Правильный и достаточно быстрый	Средняя
Устойчивый автоматизм	Низкая

При этом примеры должны перемешиваться.

Не допускается:

* постоянное повторение одного примера;
* длинные серии только одной таблицы;
* последовательное отображение 2 × 1, 2 × 2, 2 × 3;
* слишком частое повторение уже освоенных фактов.

4.4. Этап 3 — интервальное повторение

У каждого математического факта будет собственный интервал повторения.

Предлагаемая стартовая модель:

Уровень	Следующая проверка
Ошибка	Через 2–4 задания
Первый успешный ответ	В текущей тренировке позднее
Несколько успешных ответов	Через 1 день
Устойчивый навык	Через 2–4 дня
Хорошо закреплён	Через 7 дней
Долгосрочное закрепление	Через 14–30 дней

Интервалы должны корректироваться на основании последующих результатов.

Это не жёсткая схема, а начальные параметры алгоритма.

4.5. Этап 4 — контроль автоматизма

Предлагаю использовать три критерия:

Точность: ребёнок должен правильно воспроизводить ответ.

Скорость: ответ должен приходить без длительного вычисления.

Устойчивость: успешный результат должен повторяться в разные дни.

Нельзя присваивать статус мастера после трёх правильных ответов подряд в одном занятии.

Для MVP предлагаю следующие предварительные условия:

* не менее 5 успешных воспроизведений;
* минимум в 3 разных дня;
* точность последних попыток не ниже 95%;
* медианное время ответа до 3 секунд;
* отсутствие недавних ошибок.

Пороговые значения должны быть настраиваемыми. Они являются рабочей гипотезой для пилотирования, а не медицинским или педагогическим нормативом.

Важный момент о времени ответа

Нужно измерять время от момента появления задания до подтверждения ответа.

При этом:

* первое время не показывать ребёнку;
* учитывать только правильные ответы при расчёте скорости;
* отдельно учитывать ошибки;
* не награждать за скорость, если страдает точность;
* использовать медиану, а не только среднее значение.

Медиана устойчивее к случайным отвлечениям.

4.6. Как должна выглядеть одна тренировка

Я предлагаю стандартное занятие на 8–10 минут.

Этап	Длительность
Разминка знакомыми примерами	1 минута
Основная адаптивная тренировка	5–6 минут
Повторение сложных примеров	1–2 минуты
Завершение и награды	30 секунд

В одном занятии ориентировочно 20–30 заданий. Количество не должно быть обязательной нормой: ребёнок может закончить раньше.

Спринт на скорость можно оставить дополнительным режимом, но не делать его основой обучения.

5. Алгоритм адаптивного подбора заданий

Предлагаю использовать собственный упрощённый алгоритм, похожий по принципам на spaced repetition, но адаптированный именно под математические факты.

Не нужно внедрять полноценный SM-2: он изначально предназначен для более общего интервального повторения и не учитывает все особенности формирования вычислительной беглости.

5.1. Какие параметры хранить

Для каждого примера:

interface FactProgress {
  factId: string;
  attempts: number;
  correct: number;
  errors: number;
  consecutiveCorrect: number;
  responseTimes: number[];
  masteryLevel: 0 | 1 | 2 | 3 | 4;
  lastAttemptAt: number | null;
  nextReviewAt: number | null;
  masteredAt: number | null;
}

responseTimes — ограниченная история последних 10–15 корректных ответов. Полную историю попыток лучше хранить отдельно.

5.2. Распределение заданий

Каждому примеру присваивается вес.

Пример начальной модели:

Состояние	Вес
Неизвестный	5
С ошибками	7
Медленный	5
Формирующийся навык	3
Хорошо освоенный	1
Устойчивый автоматизм	0,3

Это не проценты и не вероятности. Это относительные веса для случайного выбора.

Дополнительные правила:

* не показывать одинаковый пример дважды подряд;
* не показывать один и тот же пример чаще одного раза в 3–5 заданий, кроме целевого повторения ошибки;
* не допускать длинных однотипных серий;
* учитывать давность последнего показа;
* приоритетно возвращать примеры с истёкшим интервалом повторения.

5.3. Обработка ошибок

Пример:

Ребёнок видит 7 × 8 и отвечает 54.

Тренажёр:

* Показывает правильный ответ 56.
* Спокойно сообщает: «Правильный ответ — 56. Попробуем ещё раз позже».
* Не снижает весь общий прогресс.
* Увеличивает приоритет этой пары.
* Возвращает её через несколько других заданий.
* Позже повторяет в следующем занятии.

Нельзя сразу выдавать серию одинаковых примеров: ребёнок может просто запомнить ответ на конкретный экран, а не укрепить связь в памяти.

5.4. Обработка правильных ответов

Пример:

Ребёнок правильно отвечает на 7 × 8 за 2,1 секунды.

Система:

* записывает время;
* обновляет точность;
* увеличивает счётчик успешных попыток;
* проверяет историю предыдущих дней;
* при необходимости повышает уровень мастерства;
* рассчитывает следующую дату повторения.

Время не должно быть единственным условием повышения уровня.

5.5. Отдельная логика для диагностики

Диагностика не должна смешиваться с обычной тренировкой.

Она нужна для получения исходных данных, поэтому:

* не выдаёт штрафы;
* не должна искусственно менять уровни освоения после одной попытки;
* сохраняет результаты отдельно;
* после завершения создаёт первоначальный профиль сложности.

По умолчанию можно установить испанский, но выбор языка должен быть доступен родителю.

Важно: сами математические примеры от языка не зависят.

7. Игровая механика

Здесь важно соблюдать баланс.

Игра должна поддерживать интерес, но не отвлекать от математической задачи.

7.1. Персонаж

Основной персонаж — космический лис.

У персонажа четыре состояния:

* приветствие;
* размышление;
* радость при правильном ответе;
* поддержка после ошибки.

Не нужно анимировать персонажа после каждого нажатия сложными эффектами.

7.2. Система наград

Предлагаю простую систему:

Событие	Награда
Правильный ответ	1 звезда
Серия из 5 правильных	Дополнительная звезда
Завершение занятия	2 звезды
Освоение нового факта	3 звезды
Сохранение навыка через несколько дней	5 звёзд

Скорость ответа не должна напрямую определять основную награду.

Иначе ребёнок начнёт торопиться и допускать больше ошибок.

7.3. Достижения

На первом этапе достаточно шести:

* Первые 10 правильных ответов.
* 25 освоенных фактов.
* 50 освоенных фактов.
* 100 освоенных фактов.
* Первая неделя занятий.
* Вся таблица освоена.

Достижения должны быть основаны на реальном прогрессе, а не на количестве открытий приложения.

8.1. Почему такая структура

В будущем мы добавим новую математическую операцию, например деление.

Тогда появится:

engine/
  division/
    divisionGenerator.ts
    divisionEvaluator.ts
    divisionFacts.ts

А общий движок останется прежним.

То же самое с умножением многозначных чисел:

engine/
  multiplication/
    multiplicationGenerator.ts
    multiplicationEvaluator.ts
features/
  multiplication/
    basic/
    column/
    multiDigit/

Это позволит не переписывать приложение при расширении.

8.2. Общий интерфейс математического упражнения

Предлагаю использовать типизированную модель:

export type OperationType =
  | 'multiplication'
  | 'division'
  | 'multiDigitMultiplication'
  | 'multiDigitDivision';
export interface Exercise {
  id: string;
  operation: OperationType;
  operands: number[];
  expectedAnswer: number;
  display: {
    type: 'inline' | 'column';
  };
  difficulty: number;
}

И общий интерфейс движка:

export interface ExerciseEngine {
  generate(): Exercise;
  evaluate(
    exercise: Exercise,
    answer: number
  ): boolean;
}

Это архитектурный контракт для будущих операций. В MVP реализуется только multiplication.

9. Модель хранения данных

Для проекта предлагаю IndexedDB с библиотекой Dexie.js.

Она упрощает работу с IndexedDB, поддерживает индексы и версионирование схемы.

В базе будут четыре основные таблицы.

9.1. Facts — математические факты

Хранение состояния каждого примера.

interface MathFact {
  id: string;
  operation: OperationType;
  operands: number[];
  canonicalId: string;
  attempts: number;
  correct: number;
  errors: number;
  responseTimes: number[];
  masteryLevel: number;
  nextReviewAt: number | null;
  lastAttemptAt: number | null;
  masteredAt: number | null;
}

canonicalId позволяет связывать перемножения с переставленными множителями.

Например, mul:7:8 будет идентификатором и для 7 × 8, и для 8 × 7.

9.2. Attempts — история ответов

interface Attempt {
  id: string;
  exerciseId: string;
  correct: boolean;
  responseTimeMs: number;
  createdAt: number;
  sessionId: string;
}

История нужна для аналитики и возможности в дальнейшем улучшать алгоритм.

9.3. Sessions — занятия

interface TrainingSession {
  id: string;
  mode: 'adaptive' | 'diagnostic' | 'weak';
  startedAt: number;
  completedAt: number | null;
  totalQuestions: number;
  correctAnswers: number;
  durationMs: number;
}

9.4. Settings — настройки

interface AppSettings {
  language: 'ru' | 'es';
  soundEnabled: boolean;
  dailyGoalMinutes: number;
  animationsEnabled: boolean;
}

По умолчанию:

* язык — испанский;
* звуки выключены;
* продолжительность цели — 10 минут;
* анимации включены.

9.5. Резервное копирование

Обязательно предусмотреть:

* экспорт всей базы в JSON;
* импорт резервной копии;
* проверку версии формата;
* защиту от повреждённого файла;
* предупреждение перед заменой существующих данных.

Это особенно важно, поскольку GitHub Pages не предоставляет синхронизацию между устройствами.

10. Требования к адаптации под Apple

Это отдельная часть ТЗ, потому что iOS Safari имеет свои особенности.

10.1. Поддерживаемые устройства

* iPhone с актуальной версией iOS;
* iPad с актуальной версией iPadOS;
* Safari как основной браузер;
* возможность запуска через иконку на домашнем экране.

10.2. Адаптивность

Предлагаемые точки адаптации:

iPhone	Одна колонка

Не нужно создавать три отдельных интерфейса. Используем один адаптивный дизайн.

10.3. Особенности iOS

Обязательные требования:

* корректный viewport;
* viewport-fit=cover;
* учёт env(safe-area-inset-*);
* запрет случайного выделения текста на кнопках;

* поддержка touch-событий;
* проверка сохранения IndexedDB после перезапуска Safari;
* корректная работа при переходе приложения в фон;
* восстановление незавершённой сессии после возврата.

Отдельно: приложение не должно считать время, проведённое в фоне, временем ответа на математическое задание.

Если ребёнок свернул Safari, текущий вопрос нужно приостановить и восстановить без штрафа.

В первую версию включить минимальную поддержку установки на домашний экран:

* цвет темы;

12. GitHub и развёртывание

Предлагаю использовать обычный GitHub-репозиторий с автоматической публикацией через GitHub Actions.

Порядок работы:

* Создаём репозиторий math-hero.
* Локально создаём проект через Vite.
* Разрабатываем и тестируем приложение на компьютере.
* Загружаем исходный код в GitHub.
* GitHub Actions собирает приложение.
* Результат автоматически публикуется на GitHub Pages.

Пример конфигурации Vite:

import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
export default defineConfig({
  plugins: [react()],
  base: '/math-hero/',
});

Если репозиторий будет называться иначе, base нужно изменить соответственно.

GitHub Actions:

name: Deploy Math Hero
on:
  push:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
  pages: write
  id-token: write
concurrency:
  group: pages
  cancel-in-progress: true
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./dist
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    needs: build
    steps:
      - uses: actions/deploy-pages@v4
        id: deployment

В настройках репозитория GitHub Pages выбираем источник GitHub Actions.

Важное правило: GitHub Pages должен публиковать только собранную папку dist, а не исходники из src.

Версии GitHub Actions в конфигурации зафиксированы для примера; перед публикацией стоит проверить актуальные поддерживаемые версии.

13. Тестирование и критерии готовности

Недостаточно, чтобы приложение просто отображало примеры. Нужно убедиться, что алгоритм действительно работает корректно.

13.1. Тесты математического движка

Обязательно проверить:

* генерируются все 144 направленных примера;
* нет примеров вне диапазона 1–12;
* произведения рассчитываются правильно;
* 7 × 8 и 8 × 7 связываются общим canonical ID;
* правильные ответы обновляют статистику;
* неправильные ответы повышают приоритет повторения;
* мастерство не присваивается после одного занятия;
* освоенные примеры продолжают периодически проверяться;
* повторение не зацикливается на одном примере.

13.2. Тесты адаптивного алгоритма

Смоделировать три профиля:

Профиль A — всё знает хорошо.

Ребёнок отвечает правильно и быстро. Алгоритм постепенно увеличивает интервалы.

Профиль B — знает таблицу, но долго думает.

Ответы правильные, но медленные. Алгоритм чаще возвращает соответствующие примеры, не объявляя их ошибочными.

Профиль C — отдельные пробелы.

Ошибки на 6 × 7, 7 × 8, 8 × 9. Именно эти факты должны получать повышенный приоритет.

13.3. Приёмочные испытания на iPhone и iPad

* Открытие по HTTPS.
* Прохождение полной диагностики.
* Проведение тренировки.
* Перезагрузка браузера.
* Проверка сохранности прогресса.
* Экспорт и импорт данных.
* Переключение RU / ES.
* Поворот устройства.
* Сворачивание Safari и возврат.
* Установка на домашний экран.
* Работа без интернета после первой загрузки.

16. Как я вижу дальнейшее развитие

После того как таблица умножения будет полноценно реализована и проверена, можно расширять приложение следующими модулями.

Будущая математическая платформа

Сейчас — MVP

Умножение 1–12

Автоматизм базовых математических фактов

Деление

Обратные математические факты

Умножение в столбик

Двузначные и трёхзначные числа

Деление в столбик

Деление многозначных чисел

Смешанные задания

Несколько операций в одном занятии

Здесь есть ещё один важный педагогический момент: при добавлении деления нужно будет связывать его с уже освоенными фактами умножения.

Например, если ребёнок хорошо знает 7 × 8 = 56, то 56 ÷ 7 = 8 и 56 ÷ 8 = 7 должны постепенно осваиваться как связанные факты. Это позволит использовать уже сформированные знания, а не начинать обучение заново.

17. Моя итоговая рекомендация

Я считаю, что оптимальная первая версия должна иметь три главных свойства:

* Качественный адаптивный движок. Он должен понимать разницу между ошибкой, медленным ответом и автоматическим воспроизведением.
* Удобный интерфейс для iPhone и iPad. Большие цифры, собственная клавиатура, минимум отвлекающих элементов.
* Надёжная история обучения. Приложение должно помнить результаты между занятиями, иначе интервальное повторение теряет смысл.

И самое главное — я бы не ставил цель «закрыть все 144 ячейки зелёным цветом». Это не гарантирует реального навыка. Нужно добиться устойчивого быстрого воспроизведения с проверкой в разные дни.

18. С чего начать работу на компьютере

Предлагаю следующий практический порядок:

* Установить Node.js LTS и Git.
* Создать репозиторий math-hero на GitHub.
* Создать локальный проект React + TypeScript + Vite.
* Добавить структуру каталогов из ТЗ.
* Реализовать сначала multiplicationFacts, masteryCalculator и scheduler.
* Написать тесты движка.
* Только после этого переходить к экранам и дизайну.

Мой совет: не пытаться поручить AI сразу весь проект одним запросом. Лучше разрабатывать по этапам, проверяя результат каждого этапа. Особенно важно отдельно протестировать алгоритм обучения на искусственных профилях ребёнка.

Для начала разработки можно использовать этот стартовый набор команд:

npm create vite@latest math-hero -- --template react-ts
cd math-hero
npm install
npm install dexie
npm install -D vitest @testing-library/react \
  @testing-library/jest-dom jsdom
npm run dev

В качестве следующего практического шага я рекомендую начать с Этапа 1 — создать полноценный GitHub-проект с правильной структурой, базовым дизайном, адаптивной оболочкой под iPhone/iPad и переключением RU/ES. После него отдельно реализовать и проверить математический движок. Так мы получим проект, который можно будет спокойно развивать, не превращая его в один большой файл с трудноизменяемой логикой.
