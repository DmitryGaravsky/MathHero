Technical specification: Math Hero — a mathematical fluency trainer

Status — historical MVP specification. See docs/product/REQUIREMENTS-1.1.md
for the active 1.1 release specification and docs/development/ for current
setup and release instructions. The scaffold and deployment examples below
are obsolete.

MVP · iPhone / iPad · Russian / Español

I propose a slight change to the original concept. We are building a serious adaptive trainer with a game-like presentation, rather than a children's game containing math problems.

Its main purpose is to develop stable automatic recall of the multiplication table, so that a child stops using working memory to calculate simple products and can concentrate on more complex operations.

At the same time, the architecture must allow the following additions in the future:

* division;
* multiplication of two-digit and three-digit numbers;
* division of multi-digit numbers;
* column arithmetic;
* mixed arithmetic exercises.

For now, however, we are fully addressing just one task: automatic recall of multiplication-table results from 1 to 12.

The first version will have no voice input, word problems, or complex game mechanics.

1. Product concept

1.1. Who the application is for

Primary user:

* a child aged 8–9;
* a native Russian speaker;
* studying in a Spanish-speaking educational environment;
* knows the multiplication table but does not recall answers quickly enough;
* practices on an iPad or iPhone.

The second user is a parent who:

* launches the application;
* sees progress;
* can assess weaknesses;
* understands whether automatic recall is actually developing.

1.2. Main educational goal

The goal is more than teaching a child to answer exercises correctly.

We need to achieve the following result:

* The child sees an exercise.
* The correct answer is retrieved from memory without repeated addition.
* The answer is produced quickly.
* The skill is retained after several days.
* The skill works in mixed order, not only within a single times table.

This will be the criterion for product success.

1.3. Development principles

Principle	Decision
Simplicity	A minimum of screens and actions
Mobility	Design for iPhone and iPad first
Learning	Retrieval practice + spaced practice
Adaptation	Individual difficulty for each exercise
Motivation	A character, experience, achievements
Bilingualism	Russian and Spanish interfaces
Independence	No server or registration
Extensibility	Mathematical operations as separate modules

2. Technology stack

I recommend abandoning the idea of a single large HTML file from the outset.

That is acceptable for an initial prototype, but a project that will evolve should use a proper React application structure.

Why IndexedDB instead of localStorage:

* more options for structured storage;
* a history of many attempts;
* separate records for each mathematical fact;
* the ability to add new exercise types;
* easier data-structure migration.

The MVP requires no backend, authentication, or cloud database.

An important limitation: data will remain on a particular device in a particular browser. Clearing Safari data may cause it to be lost. Therefore, the MVP must include backup export and import.

3.3. Results screen

The child sees:

* how many exercises they solved;
* how many answers were correct;
* how many exercises improved;
* how many stars they received;
* which achievement they unlocked.

The parent additionally sees:

* mean response time;
* accuracy;
* the most difficult exercises;
* changes in speed by day;
* how many exercises are reliably mastered.

Do not show the child long statistical tables. Detailed analytics belong in a separate part of the interface for the adult.

3.4. Multiplication-table map

The application must have a 12 × 12 grid.

Each cell has a color status:

Color	Meaning
Gray	Not yet assessed
Red	Errors or difficulties
Yellow	Skill developing
Light blue	Good speed and accuracy
Green	Stable automatic recall

Tapping a cell lets the user view the history of that particular exercise and practice it separately.

A special consideration: mathematically, 7 × 8 and 8 × 7 represent the same fact because of commutativity. However, both directions must appear in exercises. Internal mastery tracking will account for this to avoid artificially doubling the workload.

4. Method for developing automatic recall

This is the central part of the project. It must not be left inside React components or implemented as a handful of random conditions.

A separate training-engine module is needed.

4.1. Mathematical content

The table includes:

* multipliers from 1 to 12;
* multiplicands from 1 to 12;
* 144 directed exercises;
* 78 unique pairs when commutativity is taken into account.

Each directed exercise can appear in both orientations.

For example:

* 7 × 8 = 56;
* 8 × 7 = 56.

The database stores data for both directions, while overall mastery also takes the combined history of the pair into account.

4.2. Step 1 — initial diagnosis

On the first launch, the user is offered a diagnostic assessment.

It must:

* include all 144 directions;
* shuffle the exercises;
* show no countdown timer;
* record accuracy;
* measure response time;
* save errors.

The diagnosis must be divided into several short parts, for example, 24 exercises each.

The child can stop and continue later.

The purpose of diagnosis is to obtain an initial knowledge model, not to assign a grade.

Important: a slow correct answer on the first pass must not immediately count as a mastered fact.

4.3. Step 2 — adaptive practice

This is the main mode the child will use daily.

Selection principle:

Exercise state	Frequency
Not assessed	High
Has errors	Very high
Correct but slow	High
Correct and sufficiently fast	Medium
Stable automatic recall	Low

Exercises must also be mixed.

The following are not allowed:

* constant repetition of a single exercise;
* long runs from just one times table;
* sequential presentation of 2 × 1, 2 × 2, 2 × 3;
* overly frequent repetition of already mastered facts.

4.4. Step 3 — spaced repetition

Each mathematical fact will have its own review interval.

Proposed starting model:

Level	Next check
Error	After 2–4 exercises
First successful answer	Later in the current practice session
Several successful answers	After 1 day
Stable skill	After 2–4 days
Well consolidated	After 7 days
Long-term consolidation	After 14–30 days

Intervals must be adjusted based on subsequent results.

This is not a rigid scheme, but the algorithm's initial parameters.

4.5. Step 4 — checking automatic recall

I propose using three criteria:

Accuracy: the child must recall the answer correctly.

Speed: the answer must come without lengthy calculation.

Stability: a successful result must recur on different days.

Master status must not be awarded after three consecutive correct answers in a single session.

For the MVP, I propose the following preliminary conditions:

* at least 5 successful recalls;
* on at least 3 different days;
* accuracy of recent attempts at least 95%;
* median response time up to 3 seconds;
* no recent errors.

The thresholds must be configurable. They are a working hypothesis for piloting, not a medical or educational standard.

An important point about response time

Measure the time from the exercise appearing to confirmation of the answer.

At the same time:

* do not show the time to the child initially;
* include only correct answers when calculating speed;
* track errors separately;
* do not reward speed at the expense of accuracy;
* use the median, not only the mean.

The median is more robust to occasional distractions.

4.6. What one practice session should look like

I propose a standard session of 8–10 minutes.

Stage	Duration
Warm-up with familiar exercises	1 minute
Main adaptive practice	5–6 minutes
Review of difficult exercises	1–2 minutes
Finish and rewards	30 seconds

A session contains approximately 20–30 exercises. This number must not be a mandatory quota: the child can finish earlier.

A speed sprint may remain an additional mode, but should not be the basis of learning.

5. Adaptive exercise-selection algorithm

I propose using a simplified custom algorithm similar in principle to spaced repetition, but adapted specifically to mathematical facts.

There is no need to implement full SM-2: it was originally intended for more general spaced repetition and does not account for every aspect of developing computational fluency.

5.1. Parameters to store

For each exercise:

interface FactProgress {
  factId: string;
  attempts: number;
  correct: number;
  errors: number;
  consecutiveCorrect: number;
  responseTimes: number[];
  masteryLevel: 0 | 1 | 2 | 3 | 4;
  lastAttemptAt: number | null;
  nextReviewAt: number | null;
  masteredAt: number | null;
}

responseTimes is a limited history of the most recent 10–15 correct answers. The complete attempt history is better stored separately.

5.2. Exercise distribution

Each exercise is assigned a weight.

Example starting model:

State	Weight
Unknown	5
With errors	7
Slow	5
Developing skill	3
Well learned	1
Stable automatic recall	0.3

These are neither percentages nor probabilities. They are relative weights for random selection.

Additional rules:

* do not show an identical exercise twice in a row;
* do not show the same exercise more often than once every 3–5 exercises, except for targeted error review;
* avoid long runs of the same type;
* take time since the last presentation into account;
* prioritize returning exercises whose review interval has expired.

5.3. Handling errors

Example:

The child sees 7 × 8 and answers 54.

The trainer:

* Shows the correct answer, 56.
* Calmly says: “The correct answer is 56. We will try again later.”
* Does not reduce overall progress across the board.
* Increases this pair's priority.
* Returns it after several other exercises.
* Reviews it again in the next session.

Do not immediately present a series of identical exercises: the child may simply remember the answer to that particular screen, rather than strengthen the association in memory.

5.4. Handling correct answers

Example:

The child answers 7 × 8 correctly in 2.1 seconds.

The system:

* records the time;
* updates accuracy;
* increments the successful-attempt counter;
* checks the history from previous days;
* raises the mastery level if appropriate;
* calculates the next review date.

Time must not be the only condition for increasing a level.

5.5. Separate diagnostic logic

Diagnosis must not be mixed with ordinary practice.

It provides baseline data, so it:

* imposes no penalties;
* must not artificially change mastery levels after a single attempt;
* saves its results separately;
* creates an initial difficulty profile upon completion.

7. Game mechanics

Maintaining balance is important here.

The game must sustain interest without distracting from the mathematical task.

7.1. Character

The main character is a space fox.

The character has four states:

* greeting;
* thinking;
* joy at a correct answer;
* encouragement after an error.

There is no need to animate the character with complex effects after every tap.

7.2. Reward system

I propose a simple system:

Event	Reward
Correct answer	1 star
A streak of 5 correct answers	An additional star
Completing a session	2 stars
Mastering a new fact	3 stars
Retaining a skill after several days	5 stars

Response speed must not directly determine the main reward.

Otherwise, the child will start rushing and make more mistakes.

7.3. Achievements

Six are enough for the first stage:

* First 10 correct answers.
* 25 mastered facts.
* 50 mastered facts.
* 100 mastered facts.
* First week of practice.
* The entire table mastered.

Achievements must be based on real progress, not on the number of times the application is opened.

8.1. Why this structure

In the future, we will add a new mathematical operation, for example, division.

This will introduce:

engine/
  division/
    divisionGenerator.ts
    divisionEvaluator.ts
    divisionFacts.ts

The shared engine will remain unchanged.

The same applies to multi-digit multiplication:

engine/
  multiplication/
    multiplicationGenerator.ts
    multiplicationEvaluator.ts
features/
  multiplication/
    basic/
    column/
    multiDigit/

This will allow expansion without rewriting the application.

8.2. Shared mathematical exercise interface

I propose a typed model:

export type OperationType =
  | 'multiplication'
  | 'division'
  | 'multiDigitMultiplication'
  | 'multiDigitDivision';
export interface Exercise {
  id: string;
  operation: OperationType;
  operands: number[];
  expectedAnswer: number;
  display: {
    type: 'inline' | 'column';
  };
  difficulty: number;
}

And a shared engine interface:

export interface ExerciseEngine {
  generate(): Exercise;
  evaluate(
    exercise: Exercise,
    answer: number
  ): boolean;
}

This is an architectural contract for future operations. Only multiplication is implemented in the MVP.

9. Data storage model

For the project, I propose IndexedDB with the Dexie.js library.

It simplifies IndexedDB access and supports indexes and schema versioning.

The database will have four main tables.

9.1. Facts — mathematical facts

Stores the state of each exercise.

interface MathFact {
  id: string;
  operation: OperationType;
  operands: number[];
  canonicalId: string;
  attempts: number;
  correct: number;
  errors: number;
  responseTimes: number[];
  masteryLevel: number;
  nextReviewAt: number | null;
  lastAttemptAt: number | null;
  masteredAt: number | null;
}

canonicalId links multiplications whose factors are reversed.

For example, mul:7:8 will be the identifier for both 7 × 8 and 8 × 7.

9.2. Attempts — answer history

interface Attempt {
  id: string;
  exerciseId: string;
  correct: boolean;
  responseTimeMs: number;
  createdAt: number;
  sessionId: string;
}

History is needed for analytics and to enable future algorithm improvements.

9.3. Sessions — practice sessions

interface TrainingSession {
  id: string;
  mode: 'adaptive' | 'diagnostic' | 'weak';
  startedAt: number;
  completedAt: number | null;
  totalQuestions: number;
  correctAnswers: number;
  durationMs: number;
}

9.4. Settings — preferences

interface AppSettings {
  language: 'ru' | 'es';
  soundEnabled: boolean;
  dailyGoalMinutes: number;
  animationsEnabled: boolean;
}

Defaults:

* language — Spanish;
* sounds off;
* goal duration — 10 minutes;
* animations on.

9.5. Backups

The following are required:

* export of the entire database as JSON;
* backup import;
* format-version checking;
* protection against a corrupted file;
* a warning before replacing existing data.

This is especially important because GitHub Pages does not provide synchronization between devices.

10. Apple adaptation requirements

This is a separate part of the specification because iOS Safari has its own particular behavior.

10.1. Supported devices

* iPhone with a current version of iOS;
* iPad with a current version of iPadOS;
* Safari as the primary browser;
* the ability to launch from a Home Screen icon.

10.2. Responsive behavior

Proposed responsive breakpoints:

Device	Interface
iPhone	One column
iPad portrait	One wide column
iPad landscape	Central area with a progress sidebar

There is no need to create three separate interfaces. Use one responsive design.

10.3. iOS specifics

Mandatory requirements:

* a correct viewport;
* viewport-fit=cover;
* handling of env(safe-area-inset-*);
* prevention of accidental text selection on buttons;
* no page zoom while interacting with inputs;
* touch-event support;
* verification that IndexedDB persists after restarting Safari;
* correct behavior when the application enters the background;
* restoration of an unfinished session on return.

Separately: the application must not count time spent in the background as response time for a mathematical exercise.

If the child minimizes Safari, pause the current question and restore it without penalty.

10.4. PWA

Include minimal Home Screen installation support in the first version:

* manifest.webmanifest;
* icons;
* application name;
* theme color;
* standalone display mode.

A Service Worker and full offline caching can be implemented as a separate stage. However, the project structure must allow them to be added without reworking the application.

12. GitHub and deployment

I propose using a regular GitHub repository with automatic publishing through GitHub Actions.

Workflow:

* Create a repository named math-hero.
* Create the project locally using Vite.
* Develop and test the application on the computer.
* Upload the source code to GitHub.
* GitHub Actions builds the application.
* The result is automatically published to GitHub Pages.

Example Vite configuration:

import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
export default defineConfig({
  plugins: [react()],
  base: '/math-hero/',
});

If the repository has a different name, change base accordingly.

GitHub Actions:

name: Deploy Math Hero
on:
  push:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
  pages: write
  id-token: write
concurrency:
  group: pages
  cancel-in-progress: true
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./dist
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    needs: build
    steps:
      - uses: actions/deploy-pages@v4
        id: deployment

In the repository's GitHub Pages settings, select GitHub Actions as the source.

Important rule: GitHub Pages must publish only the built dist folder, not the source files from src.

The GitHub Actions versions in this configuration are fixed for illustration; check currently supported versions before publishing.

13. Testing and readiness criteria

It is not enough for the application simply to display exercises. We must ensure that the algorithm actually works correctly.

13.1. Mathematical engine tests

The following must be checked:

* all 144 directed exercises are generated;
* no exercises fall outside the 1–12 range;
* products are calculated correctly;
* 7 × 8 and 8 × 7 are linked by a shared canonical ID;
* correct answers update statistics;
* incorrect answers increase review priority;
* mastery is not awarded after a single session;
* mastered exercises continue to be checked periodically;
* repetition does not become stuck on one exercise.

13.2. Adaptive algorithm tests

Simulate three profiles:

Profile A — knows everything well.

The child answers correctly and quickly. The algorithm gradually increases intervals.

Profile B — knows the table but thinks for a long time.

Answers are correct but slow. The algorithm returns the corresponding exercises more often without classifying them as errors.

Profile C — specific gaps.

Errors on 6 × 7, 7 × 8, 8 × 9. These particular facts must receive increased priority.

13.3. Acceptance tests on iPhone and iPad

* Open over HTTPS.
* Complete the full diagnosis.
* Complete a practice session.
* Reload the browser.
* Verify that progress is preserved.
* Export and import data.
* Switch RU / ES.
* Rotate the device.
* Minimize Safari and return.
* Install on the Home Screen.
* Work without internet after the first load.

14. Implementation plan

I would divide development into five sequential stages.

16. My view of further development

Once the multiplication table has been fully implemented and verified, the application can be expanded with the following modules.

Future mathematical platform

Now — MVP

Multiplication 1–12

Automatic recall of basic mathematical facts

Division

Inverse mathematical facts

Column multiplication

Two-digit and three-digit numbers

Long division

Division of multi-digit numbers

Mixed exercises

Several operations in one session

There is another important educational point here: when adding division, link it to already mastered multiplication facts.

For example, if the child knows 7 × 8 = 56 well, then 56 ÷ 7 = 8 and 56 ÷ 8 = 7 should gradually be learned as related facts. This allows existing knowledge to be used instead of starting learning from scratch.

17. My final recommendation

I believe the optimal first version should have three main qualities:

* A high-quality adaptive engine. It must understand the difference between an error, a slow answer, and automatic recall.
* A convenient interface for iPhone and iPad. Large digits, a custom keypad, and minimal distractions.
* Reliable learning history. The application must remember results between sessions; otherwise, spaced repetition loses its purpose.

Most importantly, I would not set the goal of “turning all 144 cells green.” That does not guarantee real skill. The goal must be stable, fast recall verified on different days.

18. How to start work on the computer

I propose the following practical sequence:

* Install Node.js LTS and Git.
* Create a math-hero repository on GitHub.
* Create a local React + TypeScript + Vite project.
* Add the directory structure from the specification.
* Implement multiplicationFacts, masteryCalculator, and scheduler first.
* Write engine tests.
* Only then move on to screens and design.

My advice: do not try to give AI the entire project in a single request. It is better to develop in stages and check the result of each stage. Separately testing the learning algorithm on artificial child profiles is especially important.

This initial set of commands can be used to begin development:

npm create vite@latest math-hero -- --template react-ts
cd math-hero
npm install
npm install dexie
npm install -D vitest @testing-library/react \
